# 技术洞察分析

## 用途

把一条技术视频、访谈、播客、X thread 或工程/创业者内容，稳定处理成 **“先提取，再解释，再洞察，再成稿”** 的中文输出。

这不是普通摘要技能，也不是泛泛的观点评论。它的目标是：

1. 先确认**原始来源**，不要直接依赖搬运源或二手标题。
2. 先判断**字幕/转录质量**，不要把自动字幕当成逐字稿。
3. 先做**内容提取与主线恢复**，把作者/讲者原本怎么讲、怎么推进、怎么举例恢复出来。
4. 再做**关键概念、关键例子、关键逻辑链**的解释。
5. 最后输出一版适合用户吸收的中文洞察稿，重点服务独立开发、AI coding、工程判断、产品判断、增长/IP 与方法迁移。

默认适合：
- YouTube 技术演讲
- B 站搬运/转载技术内容
- AI / 编程 / 工程方法 / agent / vibe coding / 独立开发内容
- Karpathy、硅谷工程师、AI 创业者、技术 founder 的访谈和分享
- 需要整理成 B 站解说稿、公众号长文、中文分析稿、docx 成稿的内容

---

## 什么时候用

用户出现以下意图时触发：

- “分析这个视频全文讲了什么”
- “不要自己发散，先做内容提取”
- “先看来源和字幕质量再分析”
- “做成 B 站视频分析稿 / 公众号稿 / docx”
- “按全文主线拆出来，再解释关键概念”
- “保留例子，讲清楚前因后果和逻辑”
- “不要只告诉我说明了什么，要说例子具体是什么”
- “帮我提炼工程判断 / 产品逻辑 / 独立开发启发”

如果是 B 站链接，**默认先追溯原始来源**，优先找 YouTube 原视频或创作者原始发布。

## 核心原则

### 原则 1：先忠实提取，再克制解释，最后形成洞察

不要一上来就围绕某个概念自由发挥。
必须先做：

- 来源判断
- 字幕质量判断
- 内容主线提取
- 章节拆分
- 关键概念定位
- 关键例子定位
- 逻辑链恢复

然后再分析。

### 原则 2：优先主源，不迷信搬运源

如果 B 站简介里有原 YouTube 链接：
- YouTube 原视频是主分析源
- B 站只作为分发壳、标题包装、简介补充、评论语境来源

如果没有主源，要明确说明当前分析材料来自哪里，置信度如何。

### 原则 3：不要只讲概念，要讲“视频里是怎么讲出来的”

输出不能变成抽象理论文章。必须回答：

- 这支内容全文到底讲了什么
- 是按什么顺序推进的
- 哪些概念是关键概念
- 哪些例子支撑了理解
- 例子具体是什么、前因后果是什么、逻辑是什么
- 哪些结论是从前文推出来的

### 原则 4：概念解释要够用，不要写成百科

概念要解释，但只解释理解当前内容必需的那部分。

应该做：
- 用白话解释含义
- 说明它在这支内容里的作用
- 如有必要，用原视频/原文例子解释

不应该做：
- 变成独立百科条目
- 大段脱离原内容发散
- 用概念覆盖掉内容提取本身

### 原则 5：关键例子必须展开，不允许只写“说明了什么”

如果内容里有明显用于承上启下的真实例子，比如：
- 安装器
- demo
- side project
- 真实工作流
- 产品体验对比
- 多 agent 工作画面
- 智能家居 / 自动化 / agent 接管软件
- 自动研究 / 自动调参 / benchmark / swarm

必须保留，并按固定结构展开：

1. **这个例子具体是什么**
2. **前因后果和逻辑是什么**
3. **它说明了什么**

禁止只写：“这个例子说明 X 很重要。”
用户不需要空泛判断，用户需要知道例子本身、发生过程、推理关系和为什么能支撑讲者结论。

### 原则 6：识别并修复“泛泛概述”问题

如果初稿里出现以下表达，要主动补具体：

- “让 agent 展开执行” → 必须说明 agent 具体如何展开：拆任务、读取上下文、调用工具、执行命令、观察结果、修错、重试、进入 loop。
- “agent 失败” → 必须说明失败具体指什么：上下文不足、任务拆错、工具调用失败、环境判断错、执行中断、验证缺失、误解意图、循环跑偏、需要人类澄清却没问。
- “旧范式操作新系统” → 必须说明旧范式是什么：把 agent 当一次性问答框、期待一次 prompt 完成、不给背景/约束/验证、不设计 memory/tool/workflow、不做 review 与迭代。
- “系统能力” → 必须拆开：模型能力、记忆、工具、循环、人机交互、验证机制分别起什么作用。
- “这点很重要” → 不要空写重要性，要写具体机制、前因后果、讲者为什么把它放在这里。

## 来源与字幕质量流程

### 第一步：来源追溯

#### YouTube
优先顺序：
1. 官方/可提取字幕
2. 自动字幕
3. 描述区 / 时间戳 / 置顶评论
4. 音频转录 ASR

#### B站
优先顺序：
1. 简介区是否给出原始来源
2. 页面标题、简介、置顶信息
3. 若为搬运，追溯 YouTube 原视频
4. 若无可靠原源，再看站内字幕/音频 ASR

对 B 站必须先判断：
- 这是原发，还是搬运？
- 是否给了 YouTube 原链接？
- 原视频是否更适合做 transcript 提取？

#### X / Twitter
优先顺序：
1. 原作者 thread 全文
2. 引用链接、文章、视频源
3. 评论区只作辅助，不作主材料

### 第二步：字幕质量分级

不要只写“有字幕/没字幕”。使用 4 档：

#### A 级：高置信
- 官方字幕
- 人工校对 transcript
- 创作者原稿

可直接用于深分析。

#### B 级：中高置信
- 可读性较好的自动字幕
- 少量术语错误，但主线完整

可用于完整分析，但要标注少量名词误差风险。

#### C 级：中低置信
- 自动字幕噪声较多
- 专有名词识别错
- 断句混乱

需要先修术语、修章节、修逻辑链，再分析。

#### D 级：低置信
- 无字幕
- transcript 不可用
- 只能靠 ASR / OCR / 页面零散信息

可以输出，但要明确低置信，不得伪装成精准逐字解析。

### 第三步：转录文本规范化

在进入分析前，先做轻量规范化：
- 修正明显人名、公司名、产品名、模型名
- 保留关键英文术语
- 必要时补简短中文解释
- 恢复段落与论证顺序

目标是忠实恢复，不是文学润色。

### 第四步：无字幕/ASR 流程的现实处理

当用户明确要求测试或处理“无字幕版”时，优先按下面顺序执行：

1. 先尝试 YouTube transcript helper，确认是否真的没有可提取字幕/自动字幕。
2. 如果 transcript 不可用，再尝试下载音频并跑 ASR（如 Whisper）。
3. 如果 `yt-dlp` 下载 YouTube 音频被 403 / PO Token / SABR 等限制拦住，不要假装已经完成本地 ASR；必须在文档里标注环境限制。
4. 如果视频实际能提取 transcript，但用户要测试“无字幕版导出效果”，可以把 transcript 当作 ASR 等价输入继续测试结构、编号、docx 导出与低置信转录处理，但必须明确说明：这不是严格的本地音频 ASR，而是无字幕流程的等价链路测试。
5. 此类输出的字幕/转录质量不要轻易标 A/B；如果自动转录存在术语误识别，应标 C 或 D，并列出典型误识别，例如 Claude/Cloud/CL、InstantDB/Instant DV、Expo Go/ExpooGo。

原则：宁可如实说明采集链路限制，也不要为了完成任务而编造 ASR 来源。

## 固定工作流

### 阶段 1：采集层

输出至少要确认：
1. 当前链接是什么平台
2. 是否找到原始来源
3. 使用了哪份文本作为主分析材料
4. 字幕/转录质量等级是什么
5. 置信度为什么是高/中/低

### 阶段 2：内容提取层

先提取，不评论。至少要做：

1. **一句话主线**
   - 这支内容总体想回答什么问题

2. **章节拆分**
   - 按内容推进拆成若干段
   - 每段写“这一段讲什么”
   - 每段写“它在整支内容里起什么作用”
   - 如果有泛泛句，必须补“具体指什么”

3. **关键概念定位**
   - 哪些概念必须懂
   - 每个只做够用解释
   - 说明概念在原内容里的作用

4. **关键例子定位**
   - 哪些例子是理解内容的支点
   - 每个例子必须讲清楚“例子具体是什么 / 前因后果和逻辑 / 它说明什么”

5. **结论与落点**
   - 内容最后落到什么判断上
   - 哪些是讲者原意，哪些是可延展启发

### 阶段 3：分析成稿层

在提取完成后，再整理成适合发布/阅读的中文分析稿。

## 推荐输出结构（标准版）

使用以下结构，标题编号必须规范：

- 一级标题：`一、二、三……`
- 二级标题：`1.、2.、3.……`
- 三级标题：`1）、2）、3）……`

注意：如果在 docx 里手写 `1.`、`2.`，段落样式必须是 Normal，不要同时使用 Word 自动编号样式，否则会出现两个数字。

### 一、来源与字幕质量

- 来源平台
- 是否追溯到原始来源
- 主分析材料是什么
- 字幕/转录质量等级
- 置信度说明

适合表格化时，docx 中可用两列表格呈现：`项目 / 内容`。

### 二、这支内容全文到底讲了什么

- 用白话说明总主线
- 不写成摘要腔
- 如果内部列递进过程，使用二级编号 `1. 2. 3.`，但在 docx 中必须是普通段落手写编号，不使用 Word List Number 自动编号

### 三、内容章节拆分

每段尽量用这个结构：

1. **第几段 + 小标题**
   - **这一段讲什么**
   - **它在整支内容里起什么作用**
   - 如果出现抽象表达，补“具体指什么 / 怎么发生 / 特别之处是什么”

示例要求：
- 不要只写：“他把任务、意图、约束、上下文表达给 agent，让它展开执行。”
- 要写清楚：agent 展开执行通常包括接收目标、拆任务、读取上下文、调用工具、执行命令、观察反馈、修错、重试、再循环推进。

### 四、关键概念

每个概念写三件事：

1. **它是什么意思**
2. **视频/原文里为什么提它**
3. **理解时最容易误会什么**

概念解释只服务原内容，不写成百科。

### 五、关键例子

每个例子必须使用以下结构：

1. **例子标题**
   - **这个例子具体是什么**
   - **前因后果和逻辑是什么**
   - **它说明了什么**

这是本 skill 的关键质量要求。例子不能只列名字，不能只写“说明了什么”。

示例：
- 多 Codex agent 平铺屏幕：要写出多个 agent 分别做什么、人如何调度和 review、为什么这说明工程师角色从写代码转向管理数字团队。
- Dobby 智能家居：要写出它接入灯光、HVAC、窗帘、泳池、安防、摄像头，并通过 WhatsApp 交互，说明软件能力如何被折叠到统一意图接口。
- AutoResearch 一夜找到 tuning：要写出人手调的局限、agent 夜间持续实验、比较和筛选，说明它不是魔法懂科学，而是持续跑可验证闭环。
- SETI@home / Folding@home：要写出分布式并行探索与“探索贵、验证便宜”的条件。
- 安装器 / OpenClaw：要写出传统 bash 脚本写死分支，与 agent 任务规范 + 环境识别 + 错误修复 loop 的差异。

### 六、关键逻辑链

不要只写短句提纲。每条逻辑链都要写完整因果：

- 前提是什么
- 机制是什么
- 所以推出什么

好写法示例：
`1. 模型变强，不只是让“回答更好”，而是让越来越多任务第一次具备了“可交付后再验证”的条件。以前模型更像一次性回答器，现在它开始能产出中间结果、调用工具、接收反馈、继续往下走，所以真正变化不是回答质量，而是任务闭环开始成立。`

### 七、真正值得拿走的思考

重点提炼：
- 工程判断
- 产品判断
- 方法论迁移
- 对独立开发者的实际意义

不要只写口号。每条最好能落到：
- 什么工作流可以被重写
- 独立开发者应该借鉴什么
- 哪些不要借鉴
- 对产品形态、工程质量、增长/IP 有什么启发

### 八、最终成稿版

把上面的提取和判断，整理成一版可读、可发的成稿。

要求：
- 中文
- 口语化但有逻辑
- 不装腔，不咨询腔，不鸡血
- 保留原内容的关键例子和推理链
- 不为了显得深刻而偏离原内容

## 推荐输出结构（完整版 / deep）

适用于长视频、Karpathy 类技术演讲、用户明确要求“先提取再分析”的场景。

输出顺序：

一、来源与字幕质量  
二、这支内容全文到底讲了什么  
三、内容章节拆分  
四、关键概念  
五、关键例子  
六、关键逻辑链  
七、真正值得拿走的思考  
八、最终成稿版  
九、置信度说明（如需要）

注意：完整版也必须先做提取层，不允许一上来直接写长篇观点文。

## 写作要求

风格要求：
- 中文
- 像懂技术的人在把事情讲明白
- 直白、口语化，但不松散
- 有逻辑，有前因后果，有推理
- 不装腔，不咨询腔，不鸡血
- 抓主线，少空话
- 不要为了“显得深刻”而偏离原内容

建议使用的连接句：
- 说白了
- 本质上
- 真正关键的是
- 这一段不是在说 X，而是在说 Y
- 这里最容易被忽略的是
- 他真正想推进到的是
- 前因是……后果是……
- 这个例子的作用不是炫技，而是说明……

避免：
- 只会列 bullet 的流水账
- 高度抽象的泛泛评论
- 把视频分析写成自己的自说自话
- 概念解释抢掉视频主线
- 例子只列标题，不解释过程
- 每段都写“这很重要”但不说明具体机制

## docx 输出与排版规范

如果用户要求 docx，必须遵守下面规范。

### 1. 内容层要求

默认先完成内容提取与分析文本，再将最终稿整理为 docx。

推荐 docx 结构：

一、来源与字幕质量  
二、这支内容全文到底讲了什么  
三、内容章节拆分  
四、关键概念  
五、关键例子  
六、关键逻辑链  
七、真正值得拿走的思考  
八、最终成稿版

### 2. 编号规范

必须统一：

- 一级：`一、二、三、四……`
- 二级：`1.、2.、3.……`
- 三级：`1）、2）、3）……`

### 3. Word/docx 自动编号坑

如果文本里已经手写 `1.`、`2.`、`3.`：

- 段落样式必须设为 `Normal`
- 不要使用 Word 的 `List Number` 自动编号样式
- 否则用户打开后会看到两个数字，例如自动编号 + 手写编号叠加

这是已验证过的真实 bug，必须避免。

### 4. 字面换行 bug

如果内容源来自聊天文本、markdown 中转文本、或其他可能把换行写成字面 `\n` 的流程，不要只在原 docx 上改样式。

必须先检查 docx 段落文本里是否存在字面 `\n`：
- 若存在，说明正文被错误写成了单段纯文本
- 必须先把字面 `\n` 还原成真正段落/换行结构，再重新生成 docx
- 不要把这种文本层 bug 误当成排版问题

### 5. docx 排版建议

- 标题居中，统一中文字体
- 一级标题加粗，可使用 13pt 左右
- 二级编号可以加粗，但不要用自动编号样式
- 正文使用普通段落
- 来源信息、关键对比、概念辨析等适合做表格的内容，优先表格化
- 表格只加在确实帮助区分和横向阅读的地方，不为“显得专业”而滥加

### 6. 交付前验证

交付 docx 前必须用脚本重新读取 docx 验证：

- 确认不再含有字面 `\n`
- 确认手写 `1.` 段落不是 `List Number` 样式
- 确认不存在行首残留的错误编号，如不该出现的 `1）`
- 确认段落数量和表格数量符合预期
- 如果用户指出某章编号有两个数字，优先检查 Word 自动编号样式残留

可用验证思路：
- 用 `python-docx` 读取 `doc.paragraphs`
- 对行首 `^\d+\.\s` 的段落检查 `p.style.name != 'List Number'`
- 检查 `p._p.pPr.numPr` 是否残留自动编号

## 质量门槛

一篇合格输出，读完后用户应该能感觉到：

- 我知道这支内容全文在讲什么了
- 我知道它是怎么一步步推进的了
- 我知道哪些概念真重要了
- 我知道例子具体发生了什么、为什么不能省了
- 我知道哪些判断是讲者原意，哪些是后续可延展思考
- 我能把其中一部分方法迁移到自己的独立开发、AI coding、产品设计或内容/IP 建设里

如果输出只做到“观点很多”，但没恢复内容主线和例子逻辑，就不合格。

## 最终提醒

这个 skill 成功的标准不是“看起来分析得很聪明”，而是：

- 先把源内容抓稳
- 再把主线抽出来
- 再把关键概念、关键例子和逻辑链讲明白
- 最后才输出有独立开发价值的洞察稿

一句话说：
**先忠实提取，再具体解释，最后形成克制但有用的技术洞察。**
